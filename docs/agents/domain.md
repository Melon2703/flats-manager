# Domain docs

This is a single-context project.

## Before exploring or designing

- Read root `GLOSSARY.md` and use its terms in specifications, tickets, and code.
- Read relevant decisions in `docs/adr/` when present.
- If either is absent, proceed silently. Create glossary entries or ADRs lazily when a real term or qualifying decision is resolved.

## Updating the model

Keep the glossary limited to concise domain definitions, without implementation details. Use the domain-modeling skill when resolving terms or recording decisions.

If a proposal conflicts with an existing ADR, identify the conflict explicitly and explain why reconsideration is warranted.
